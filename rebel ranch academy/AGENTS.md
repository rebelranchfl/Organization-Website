# Rebel Ranch Academy — Mandatory Agent Entry Point

**Status:** CONTROLLING RRA AGENT INSTRUCTION  
**Effective:** 2026-09-06  
**Scope:** This file applies to every file, folder, project, workflow, visual, course, document, research task, code change, database action, automation, publication, and other work under or for Rebel Ranch Academy.

This file supplements `/AGENTS.md`. If an older RRA document conflicts with a newer explicit owner directive, STOP and surface the conflict. Do not silently choose or improvise.

# 1. EVERY RRA TASK STARTS HERE

Do not rely on memory from an earlier turn, chat, agent run, or prior reading.

At the beginning of **every new RRA task, handoff, agent run, or materially new owner instruction**, read this file and apply its gates to the exact requested work.

The owner has explicitly rejected a workflow where rules are read once and then forgotten while work continues.

# 2. CONTROLLING RULE

**NOTHING HAPPENS UNLESS IT IS VERIFIED FIRST.**

Verification happens **before action**.

If a required fact, source, asset, owner approval, current state, wording, file, requirement, or dependency can be verified, verify it before acting.

If required verification cannot be completed:

**STOP → mark NOT VERIFIED → explain what is missing.**

Do not guess, substitute, approximate, recreate, infer, invent, or work around the missing verification.

# 3. TWO MANDATORY GATES

## Gate A — Task / turnover gate

Run this gate every time:

- a new RRA task starts;
- another agent takes over;
- a new chat/session continues RRA work;
- the owner materially changes the instruction;
- work moves into a different RRA stage or discipline.

Before work:

1. Read `/AGENTS.md`.
2. Read this `/rebel ranch academy/AGENTS.md`.
3. Identify the exact RRA program/project and requested outcome.
4. Read the current project/status record for that project when one exists.
5. Read only the controlling standards relevant to the requested action; do not blindly create or read additional documents merely because they exist.
6. Check the owner's newest explicit instruction against older documentation.
7. Identify what must be verified before the first action.
8. If instructions conflict or required verification is missing, STOP.

## Gate B — Immediate pre-action gate

Run this gate **immediately before every consequential action**, including:

- GitHub create/update/delete/move/rename/commit;
- image generation or image editing;
- document generation;
- website/code change;
- database/Supabase change;
- automation/workflow change;
- deployment/publication;
- factual regulatory/reimbursement/compliance claim;
- pricing or offer creation;
- use of a logo, tagline, catchphrase, brand color/system, or branded visual;
- declaration that something is fixed, complete, live, ready, approved, reimbursable, or verified.

Ask and answer:

1. **What exact action am I about to take?**
2. **Did the owner authorize this exact action/scope?**
3. **What facts/assets/wording/state must be true for this action to be correct?**
4. **Have those exact inputs been verified from the controlling source?**
5. **Am I about to introduce anything the owner did not approve?**
6. **Am I expanding scope instead of finishing the defined work?**
7. **Can I verify the result after the action?**

Any required `NO`, `UNKNOWN`, or unresolved conflict means **DO NOT EXECUTE THE ACTION**.

# 5. BRAND / IMAGE HARD GATE

Before ANY RRA/RRM branded visual is generated, edited, published, or integrated:

1. Verify the exact program/brand.
2. Locate the canonical approved logo file.
3. Make the **actual verified logo asset** available to the production tool when the tool needs an image source.
4. Verify every existing tagline/catchphrase from an approved source.
5. Any new proposed tagline/catchphrase/recurring brand language requires explicit owner approval **before** it appears in production material.
6. Generate/create only after steps 1–5 pass.
7. Inspect the result against the verified logo and wording.
8. If the tool redraws, approximates, alters, replaces, misspells, or invents branding, the result FAILS and must not be presented as valid branded work.

A written description of the logo is never a substitute for supplying the verified logo asset when the tool needs the asset.

# 6. FACT / COMPLIANCE HARD GATE

For PEP, HEIP, EMA, reimbursement, legal, tax, safety, technical, or other consequential factual claims:

- use the current controlling source;
- verify the date/version when rules can change;
- record conflicts instead of choosing the convenient version;
- do not convert an inference into a confirmed rule;
- do not say an expense is reimbursable unless the current applicable PEP material supports that conclusion;
- do not say an RRA/EMA process works until the actual required process has been verified.

# 7. OWNER LANGUAGE AND SCOPE

Explicit owner instructions control.

Do not replace them with:

- AI defaults;
- conventional curriculum patterns;
- generic best practices;
- extra features;
- extra documents;
- extra pages;
- extra branding;
- unrequested cleanup;
- assumptions about what would be helpful.

RRA projects use fixed scope. New useful discoveries go to Future Expansion / the applicable late-finding route unless they are necessary to achieve the approved current-version outcome.

**FINISH THE DEFINED VERSION BEFORE EXPANDING IT.**

# 8. PLAIN LANGUAGE / LEARNER EXPERIENCE

RRA material must be understandable to ordinary children and adults.

Use the simplest accurate language first. Explain technical terms in normal language. Use realistic imagery when seeing the object/process materially improves understanding.

Do not turn RRA into textbook filler. Follow the educational method:

**UNDERSTAND → EXPLORE → COMPARE → APPLY → CREATE**

# 9. END-TO-END STATUS RULE

Never call work `fixed`, `complete`, `implemented`, `live`, `ready`, `resolved`, `verified`, or equivalent unless the exact requested outcome has been proven end to end.

A commit proves a repository write, not deployment.
A generated image proves generation, not brand compliance.
Code existing proves code exists, not that the user flow works.
A created document proves creation, not that agents are forced to use it.

Report exactly:

- what was verified;
- how it was verified;
- what remains unverified.

# 10. DOCUMENT CONTROL RULE

The repository already contains many Academy standards, handoffs, implementation notes, historical records, and project files.

Do **not** respond to every new decision by creating another Markdown file.

Before creating a new documentation file:

1. inventory the relevant existing documentation;
2. determine whether an existing controlling/workflow/program document should be updated instead;
3. create a new file only when it has a distinct durable purpose that cannot be cleanly integrated into the existing structure;
4. keep controlling rules separate from program/project records and historical/archive material;
5. mark obsolete/historical material clearly rather than allowing multiple files to appear simultaneously controlling.

The intended documentation hierarchy is:

```text
REPOSITORY CONTROL
  /AGENTS.md
  /docs/ organization-wide controlling sources

PROGRAM CONTROL
  /rebel ranch academy/AGENTS.md
  RRA core direction / method / workflow controls

PROGRAM / LEARNING AREA
  documents specific to that Academy area

PROJECT
  one durable project record + required research/source/product records

HISTORY / ARCHIVE
  superseded handoffs, old implementation records, backups, historical material
```

# 11. TURNOVER CHECK

Before handing RRA work to another agent/session:

1. verify the durable project/status record reflects the true current state;
2. record the exact last completed and verified step;
3. record the next authorized step;
4. record blockers/unverified items;
5. do not make the next agent reconstruct current state from chat history;
6. point the next agent to this `AGENTS.md` first.

# 12. FAILURE RULE

If an agent discovers it violated an owner instruction or verification gate:

1. STOP the affected production path;
2. do not defend or rationalize the deviation;
3. identify the exact failed gate;
4. mark affected output invalid/unverified as appropriate;
5. correct the workflow/control point before resuming production;
6. verify the correction itself.

The purpose is not to create more paperwork. The purpose is to prevent the same failure from recurring.
