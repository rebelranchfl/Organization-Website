# RRA-2026-0004 — Product Architecture

## Product identity

**Working public product name:** Build My Water Storage System  
**Research/project title:** Containers Are Containers — Safe Storage by Function  
**Learning area:** Sustainability & Agriculture  
**Frameworks:** Think Like a Rebel; Function Before Form; Use What You Have  
**Primary audiences:** households, homesteads and mixed-use rural learners who manage more than one water-storage job  
**Secondary audiences:** emergency-preparedness learners, livestock owners and growers within the approved evidence boundaries  
**Role:** free entry tool + paid interactive planning product  
**Delivery direction:** integrated web experience with printable/offline personalized result; technical/evidence depth optional

No public price, release or sale is authorized by this architecture.

## Learner outcome

By the end, the learner can:
- identify the actual storage jobs they need;
- inspect containers they already own before shopping;
- rule out obvious inappropriate potable reuse cases;
- understand which functions different uses share and where they branch;
- calculate capacity and approximate stored-water weight;
- assign containers to suitable/conditional/non-potable/do-not-use/verify-first categories by branch;
- identify closure, dispensing, cleaning, support, placement and maintenance gaps;
- build a living multi-use storage plan;
- know exactly which unknown requires verification instead of treating every unknown as a stop sign.

The product does not promise that a generic container classification proves microbiological water safety, does not set unsupported livestock/crop thresholds, and does not certify a vessel/material for uses beyond the evidence supplied.

## Product structure

### FREE ENTRY — Can I Use This Container?
A short, useful tool that asks:
1. What do you need the water for?
2. What did the container hold before?
3. What do you know about its material/condition?
4. How does it close and dispense?
5. Can you clean and inspect it?
6. Where will it sit?

Output: branch-specific quick classification + one or two next actions.

This must provide standalone value; it is not a teaser that withholds the safety-critical answer.

### PAID CORE — Build My Water Storage System
The complete multi-use experience below.

## Complete learner sequence

### 1. Start With the Job
**Purpose:** break the form-first habit.  
**Visual:** recognizable lineup of jug, barrel, tote, tank and trough with the same question over all of them: `What job does it need to do?`  
**Action:** multi-select intended uses.  
**Output:** branch list.

### 2. Use What You Have
**Purpose:** inventory before buying.  
**Visual:** simple photo/illustration-style container inventory, not technical diagram first.  
**Action:** add each existing container and known history.  
**Output:** personal inventory.

### 3. The History Gate
**Purpose:** stop unsafe label-based assumptions.  
**Visual:** prior-contents path: water/food → unknown → chemical/pesticide/petroleum.  
**Action:** confirm what is known.  
**Output:** immediate potable exclusions / verify-first items.

### 4. See What Makes a Storage System Work
**Purpose:** teach container anatomy and failure points.  
**Primary visual:** cutaway/anatomy view showing lid/opening, vent, outlet/spigot, cleaning access, base/support, label/date, sun/chemical exposure and contamination paths.  
**Action:** inspect own container against anatomy.  
**Output:** correction list.

### 5. What Each Water Job Needs
**Purpose:** keep multi-use complexity understandable.  
**Visual:** shared-source / parallel-branch map.  
**Action:** inspect branch requirements.  
**Output:** each container assigned branch-by-branch rather than one universal verdict.

### 6. Capacity, Weight & Redundancy
**Purpose:** turn gallons into a usable physical plan.  
**Visual:** side-by-side `one 55-gallon container` vs `multiple smaller containers`, showing approximate weight, portability and single-point-of-failure differences.  
**Action:** enter target capacity / household emergency planning inputs where applicable.  
**Output:** capacity gap/surplus, approximate water weight, container options.

### 7. Fix What Matters First
**Purpose:** separate critical correction from optional upgrade.  
**Action order:**
1. disqualifying prior use / contamination path;
2. unstable support/placement;
3. closure/dispensing/cleaning failure;
4. insufficient capacity;
5. maintenance gaps;
6. optional convenience upgrades.

**Output:** prioritized action plan.

### 8. Storage Is an Operating System
**Purpose:** teach maintenance, not one-time purchase.  
**Visual:** fill → label → inspect → clean → rotate/maintain → verify after concern → correct.  
**Action:** choose realistic recurring checks.  
**Output:** maintenance schedule.

### 9. Does Function Before Form Hold Water?
**Purpose:** responsible experiment / observation.  
**Action:** inspect one real container, assign a job, observe use/failure points, improve the system, decide if it still fits.  
**Permanent rule:** successful operation is not proof of water quality when a quality question requires testing.

### 10. My Water Storage Plan
**Purpose:** deliver the product's tangible value.  
**Output:**
- selected uses;
- container inventory;
- branch assignments;
- hard exclusions and specific reasons;
- verify-first unknowns;
- capacity/weight plan;
- shared infrastructure;
- branch-specific corrections;
- maintenance plan;
- optional upgrades;
- next learning path.

The plan updates when earlier inputs change.

## Optional depth hierarchy

Default: plain language and familiar visuals.

Learner-chosen depth:
- Why?
- Show contamination paths
- Show the weight math
- Technical details
- Evidence / sources

Depth must open in-context or return to the exact learner position with state preserved.

## Personalization logic

Personalization is material, not cosmetic. At minimum the plan changes based on:
- selected uses;
- prior container history;
- known/unknown condition/material information;
- dispensing/closure/cleanability;
- capacity;
- placement/exposure;
- branch requirements;
- maintenance state.

Two materially different learner profiles must not receive the same generalized paragraph with swapped labels.

## State contract

Persist on the device/session through normal product navigation:
- selected use branches;
- container inventory;
- each container's inspection answers;
- calculated capacity targets;
- classification/correction outputs;
- maintenance choices;
- learner depth preference where useful.

Changing an earlier answer recalculates dependent branch assignments and plan outputs where practical.

## Visual-production requirements

Visual Production must build actual explanatory visuals, not styled text blocks claiming to be visuals.

Minimum visual set:
1. familiar container lineup / job-first opening scene;
2. container-history decision visual;
3. labeled container anatomy cutaway;
4. contamination-entry / dispensing comparison;
5. multi-use shared-infrastructure branch map;
6. capacity/weight/redundancy comparison;
7. maintenance loop;
8. learner's personalized system map.

## Safety / evidence boundaries

Use a short targeted warning only where the actual action presents a material immediate risk, including:
- never use prior toxic chemical/pesticide/petroleum vessels for potable storage;
- full large containers can impose substantial weight/support hazards;
- produce-contact/postharvest agricultural uses require stronger specific evidence than generic irrigation guidance.

Do not fill the product with generic legal/compliance warnings.

## Paid-value requirement

A paid product passes only if the learner receives a useful, personalized system plan and performs less independent research/comparison/design work because RRA completed that synthesis.

`More cards + more text + a printable checklist` fails.

# TRANSFER THE PRINCIPLE

Requirements follow the job. Inventory resources, understand history and constraints, identify required functions, choose forms only after that, inspect failure modes, verify what matters, then transfer the same thinking to another system.
